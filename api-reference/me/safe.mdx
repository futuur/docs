Your [Safe](https://safe.global) smart account holds the collateral you trade with. This page covers the endpoints that register it, report its state, relay its ERC-4337 UserOperations, and give the pool the standing allowance that bids need.

<Note>
  These endpoints are part of phase one and run on the preview host only. See [Environment](/environment) for the chain and addresses. They are not live on `https://api.futuur.com`.
</Note>

| Endpoint | Purpose | API keys |
|---|---|---|
| [`POST /me/safe/`](#register-your-safe) | Register the Safe address | Not allowed |
| [`GET /me/safe-wallet/`](#read-your-safe) | Read deploy state and balance | Allowed |
| [`POST /me/safe/deployed/`](#confirm-deployment) | Tell the API the Safe was deployed | Allowed |
| [`GET /me/safe/trading-status/`](#trading-status) | Check the pool allowance | Allowed |
| [`POST /me/safe/enable-trading/`](#enable-trading) | Submit the signed `approve` UserOperation | Allowed |
| [`POST /me/safe/sponsor-user-operation/`](#relay) | Get paymaster data for a UserOperation | Allowed |
| [`POST /me/safe/submit-user-operation/`](#relay) | Send a signed UserOperation | Allowed |
| [`GET /me/safe/user-operation-receipt/`](#relay) | Read a UserOperation receipt | Allowed |
| [`POST /me/safe/pimlico-rpc/`](#relay) | Allowlisted bundler JSON-RPC | Allowed |

[Withdrawing USDC](#withdraw-from-the-safe) uses the relay endpoints and is not available to API keys.

## Authentication

<Note>
  All endpoints require authentication. `POST /me/safe/` only accepts a wallet sign-in session. The others also accept HMAC headers (`Key`, `Timestamp`, `HMAC`). See the [authentication guide](/authentication).
</Note>

<Warning>
  The relay and enable-trading bodies contain a nested `user_operation` object. With HMAC, a nested value is signed as its Python `repr`, so sign these requests from Python or use a wallet session. See [How values become text](/authentication#how-values-become-text).
</Warning>

## Register your Safe

```
POST https://web3-phase-01-preview.staging.cloud.futuur.com/v2.0/me/safe/
```

Stores the address of your Safe for the active chain. The call is idempotent for the same address. It does not deploy anything.

An HMAC API key cannot call this endpoint. It returns `403` with code `permission_denied` and detail `This action is not available to API keys.` Register the Safe while signed in with your wallet. The Futuur web app does this for you on first sign-in.

<ParamField body="safe_address" type="string" required>
  The address of the Safe owned by your wallet.
</ParamField>

<ParamField body="chain_id" type="integer">
  Optional. Defaults to the active chain. Any other value is rejected.
</ParamField>

### Rules

The address is accepted only when all of these hold:

- Your account has a `wallet_address`. That EOA is the Safe owner.
- The address is not your owner EOA itself.
- You have no Safe registered yet, or you are sending the same address again. A registered Safe **cannot be changed**.
- The address is not registered to another account.
- If a contract already exists at the address, it is a 1-of-1 Safe whose only owner is your `wallet_address`. A Safe that is not deployed yet is accepted as a predicted address and checked the same way once it has code.

A rejected address returns `400` with `attr: "safe_address"` and one of these messages:

| Message | Cause |
|---|---|
| `Invalid Safe address format` | Not a 20-byte hex address |
| `A wallet address is required before registering a Safe.` | The account has no `wallet_address` |
| `Safe address cannot be the owner wallet address.` | You sent the EOA |
| `A different Safe is already registered for this account.` | You tried to change the Safe |
| `This Safe is already registered to another account.` | The address belongs to someone else |
| `Safe is not a 1-of-1 Safe owned by the user wallet address.` | Wrong owner set or threshold |
| `<address> is not a Safe contract.` | The contract at the address is not a Safe |
| `Could not verify Safe ownership on-chain; try again.` | The chain read failed |
| `This Safe is being registered; try again shortly.` | A concurrent registration of the same address |

### Response

Returns `200 OK` with the [Safe wallet object](#safe-wallet-object) plus a `migration` object describing the legacy-balance migration check (it includes a `reason`).

## Read your Safe

```
GET https://web3-phase-01-preview.staging.cloud.futuur.com/v2.0/me/safe-wallet/
```

<ParamField query="chain_id" type="integer">
  Optional. Defaults to the active chain.
</ParamField>

<ParamField query="refresh" type="string">

## Enable trading

```
POST https://web3-phase-01-preview.staging.cloud.futuur.com/v2.0/me/safe/enable-trading/
```

Submits a **signed** ERC-4337 UserOperation in which your Safe calls `approve(poolAddress, amount)` on the collateral token, then waits until the allowance is visible on-chain. Do this once per currency. After it succeeds, bids need no per-order approval.

<ParamField body="user_operation" type="object" required>
  A complete EntryPoint v0.7 UserOperation, signed by the Safe owner. The API checks that:

  - `sender` is your registered Safe,
  - `signature` is not empty,
  - `callData` is a Safe `executeUserOp` call that makes a plain, zero-value call to `approve(pool, amount)` on the token of `currency`.

  Any other call is rejected. Approve `approveAmountRaw` from the trading status: `enabled` only turns `true` for an allowance of at least half the maximum `uint256`.
</ParamField>

<ParamField body="currency" type="string" default="USDC">
  `USDC` or `OOM`. Must match the token the UserOperation approves.
</ParamField>

<ParamField body="chain_id" type="integer">
  Defaults to the active chain.
</ParamField>

### Response

Returns `200 OK` with the [trading status](#trading-status) fields plus:

<ResponseField name="alreadyEnabled" type="boolean">
  `true` when the allowance was already in place. Nothing was submitted.
</ResponseField>

<ResponseField name="userOperationHash" type="string | null">
  Hash of the submitted UserOperation, or `null` when `alreadyEnabled` is `true`.
</ResponseField>

<ResponseField name="confirmedAt" type="string">
  When the allowance was confirmed. Present only when a UserOperation was submitted.
</ResponseField>

The request blocks while the API polls the allowance, for up to about 20 seconds.

### Errors

Every failure returns `400` in the [two-entry form](/errors#on-chain-order-errors-look-different) with code `trading_not_enabled`. Read the message:

| Message | What to do |
|---|---|
| `user_operation.signature is required. Sign after POST /me/safe/sponsor-user-operation.` | Sign the UserOperation after you merge the paymaster fields |
| `No Safe registered for this chain. POST /me/safe/ with safe_address and chain_id first.` | Register the Safe |
| `Safe is not deployed on-chain yet.` | Deploy the Safe |
| `user_operation.sender does not match your registered Safe address` | Use your Safe as `sender` |
| `user_operation must be approve(pool, amount) on the settlement token` | Build the call against `collateralToken` and `poolAddress` from the trading status |
| `Invalid Safe UserOperation signature (AA24). ...` | The owner signature does not match the final UserOperation. Sign after sponsorship |
| `Approval UserOperation was submitted but standing allowance was not confirmed in time. ...` | Wait, then check the trading status again before resubmitting |

## Relay

The API relays UserOperations for your Safe to its bundler and paymaster so you do not need your own. The relay accepts only these operations from your registered Safe:

- the **deploy** operation: a zero-value call from the Safe to itself with empty data,
- **`approve(pool, amount)`** on a collateral token, and
- a **USDC withdrawal**, `transfer(to, amount)`, for wallet sign-in sessions only. See [Withdraw from the Safe](#withdraw-from-the-safe).

Anything else returns `400` with the message `This UserOperation is not allowed through the relay`. If you send `entry_point`, it must be the EntryPoint in [Environment](/environment).

### Sponsor a UserOperation

```
POST https://web3-phase-01-preview.staging.cloud.futuur.com/v2.0/me/safe/sponsor-user-operation/
```

<ParamField body="user_operation" type="object" required>
  The unsigned UserOperation. `sender` must be your registered Safe.
</ParamField>

<ParamField body="chain_id" type="integer">
  Defaults to the active chain.
</ParamField>

<ParamField body="entry_point" type="string">
  Optional. Must be the supported EntryPoint.
</ParamField>

Returns `200 OK` with the paymaster's `pm_sponsorUserOperation` result, unchanged. Merge those fields into the UserOperation, then sign it with the owner key.

### Submit a UserOperation

```
POST https://web3-phase-01-preview.staging.cloud.futuur.com/v2.0/me/safe/submit-user-operation/
```

Takes the same body with the **signed** UserOperation. Returns:

```json Sample response (200 OK)
{
  "userOperationHash": "0x..."
}
```

### Read a receipt

```
GET https://web3-phase-01-preview.staging.cloud.futuur.com/v2.0/me/safe/user-operation-receipt/?user_operation_hash=0x...
```

Returns the bundler's receipt, or `{}` while the UserOperation is not yet included. `hash` is accepted as an alias of `user_operation_hash`. `chain_id` is optional.

### Bundler JSON-RPC

```
POST https://web3-phase-01-preview.staging.cloud.futuur.com/v2.0/me/safe/pimlico-rpc/
```

A JSON-RPC pass-through for smart-account client libraries.

<ParamField body="method" type="string" required>
  One of `pm_sponsorUserOperation`, `eth_sendUserOperation`, `eth_estimateUserOperationGas`, `eth_getUserOperationReceipt`, `pimlico_getUserOperationGasPrice`. Other methods are rejected.
</ParamField>

<ParamField body="params" type="array" required>
  The JSON-RPC parameters. For the first three methods, `params[0]` is the UserOperation (same restrictions as above) and `params[1]` must be the supported EntryPoint.
</ParamField>

<ParamField body="chain_id" type="integer">
  Defaults to the active chain.
</ParamField>

Returns `200 OK` with `{"result": ...}`. A bundler error is also a `200`, shaped `{"error": {"message": "...", "code": ..., "data": ...}}`. A request the relay refuses is a `400`.

## Withdraw from the Safe

To move `USDC` out of your Safe, relay a UserOperation whose **single call** is `transfer(to, amount)` on the USDC token:

1. Build the UserOperation with your Safe as `sender`.
2. `POST /me/safe/sponsor-user-operation/` and merge the paymaster fields.
3. Sign it with the owner key.
4. `POST /me/safe/submit-user-operation/`. Keep the returned `userOperationHash`.
5. Poll `GET /me/safe/user-operation-receipt/?user_operation_hash=...` until the receipt is returned.

Rules:

- `USDC` only. `OOM` cannot be withdrawn.
- It is a plain, zero-value call to the USDC token with exactly `transfer(to, amount)`.
- `to` is not the zero address, the token itself, or the pool.
- `amount` is greater than zero, in raw units (6 decimals).
- You are signed in with your wallet. A request authenticated with an **HMAC API key is refused**.
- It is sent with `submit-user-operation`. Through `pimlico-rpc` a withdrawal can be estimated and sponsored, but `eth_sendUserOperation` is refused.

A UserOperation that breaks a rule returns `400` with `This UserOperation is not allowed through the relay`.

### Relay errors

Relay failures return `400` with the message in the entry whose `attr` is `detail`. When the bundler rejected the call, further entries whose `attr` starts with `pimlico` carry its error data.
